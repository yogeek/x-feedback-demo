Two kinds of AI model, two kinds of reader

LLMs write for people. System One models, decision models like Jev and extraction models like Clairic, answer for code. What each one does, how it works, and when to use which, or both.

The real difference: who reads the answer

LLMs are built for people

  • Trained to write replies that people prefer (RLHF) or that pass a check, like a math answer (RLVR)
  • The output is text: a chat reply, an essay, code, sometimes a refusal
  • A person reads it, judges it, and corrects it if needed

"Here is a summary of the 581 replies: most viewers found the episode…"

System One models are built for code

  • Trained to return decisions with calibrated probabilities (RLCD)
  • The output is typed data, defined in advance: an option, a score, a probability
  • A program reads it and branches on it, with no human in between
if answer.noul > 0.7:
    route_to_support(ticket)

TypeSafe's bet: most AI automation will be software talking to software, so the interface for machines matters more than the chat interface.

Where the name comes from

Daniel Kahneman, Thinking, Fast and Slow: people think with two systems.

1

System 1: fast and intuitive

You read a reply and know right away that it is angry. No steps, no words in your head.

System One models: one quick judgment, a few hundred milliseconds to a second or two

2

System 2: slow and deliberate

You plan a trip or check a proof step by step, putting each step into words.

LLMs, and reasoning LLMs even more: they think by writing, token after token

System 1 is known to make mistakes. These models bet that a fast judgment can be made reliable when it comes with an honest probability.

Same reply, same question, two ways to answer

"The lip sync is off and the voice acting feels flat, but the landscapes in Episode 1 look amazing."

An LLM writes the answer

{"opinion": "mixed"}
  1. Generates one token at a time; each one is billed
  2. Your code parses the text. Badly formed JSON means a lost answer.
  3. No sign of how sure it is

A decision model scores every answer

mixed1.00
negative0.00
positive0.00
  1. Reads the reply and the possible answers once
  2. Returns a probability for each answer, all at once. It writes nothing.
  3. Only the input is billed. The answer is always one of the options.

A decision model answers typed questions

You send a state (the text or data to judge) and a few questions. Each question has a type that fixes the shape of the answer.

Noul

Is this statement true?

noul: 0.99

"The writer asks to be contacted." A probability between 0 and 1.

Choice

Which option fits?

choice: "mixed"

One option from your list, with a probability for every option.

Score

Where on this scale?

score: 1.36

Levels you describe ("no criticism" to "insulting"); the score sits between "mild" and "strong".

Box

Where is it in the image?

top, left, bottom, right

Jev, still experimental: the edges of the object, as fractions of the image.

Questions in one request are answered in parallel and do not see each other. Your code combines the answers: the logic stays in code, where you can test it.

Extraction models: typed values out of messy input

The second family of System One models, opened by Cloudflare's Clairic. A decision model picks among your options; an extraction model returns values: a span of the text, a number, a date.

Hi, order A-88412 arrived broken. I paid $129.90 on October 2. The lid is cracked and the box was soaked.

  • Text values are spans with their position: they can be highlighted in the source and cannot contain an invented digit.
  • A missing field comes back as null with p_null, instead of a plausible-looking guess. Code sends low-confidence values to a person.
  • All fields are answered in one pass: thirty fields cost about the same as three.

Illustrative values in the response shape documented by Cloudflare. Clairic runs on Workers AI as @cf/cloudflare/clairic (preview), $0.10 per million input tokens, no output billed.

Extract, compute, estimate, forecast

You describe each field with a type and a plain-language instruction. The type fixes the shape of the answer.

text

Copy a piece of the input

"A-88412", span [10, 17]

number

Read or compute a number

141.59

Price plus tax: one or two steps of arithmetic.

date, time, duration

A valid date or length

2026-10-02

"next Thursday" resolved against a reference date.

list

Every matching value

["A-88412", "A-88415"]

In the order they appear.

estimate

A value the text does not state

median 415,000, 80%: 370k to 470k

A home price from comparable sales, within bounds you set.

forecast

The next steps of a series

one interval per step

Basic patterns, up to 64 steps.

Cloudflare's own advice: let Clairic read the values and let code do long calculations. Multi-step arithmetic and sums over many rows are not reliable yet.

A probability you can act on

Calibrated means: among all the answers given with probability 0.8, about 80% are right. So code can set a rule on it.

below 0.3treat as noact automatically
0.3 to 0.7not suresend to a person or a bigger model
above 0.7treat as yesact automatically
  • The thresholds are yours, set by the cost of each mistake: blocking a good message, or letting a bad one through.
  • An LLM can say "I am 90% sure", but that number is written text, not a measured probability.
  • Calibration holds across many answers, not for each single one. Check it on a labeled sample before trusting it.

"But Sonnet wins. Why use Jev?"

93%

Sonnet is graded against itself

The answer key is Sonnet's own labels from an earlier run, so "right answers" means "agrees with Sonnet". Even so, Sonnet changes its answer on 7 to 9% of replies from one run to the next. Any model that judges like Sonnet gets a bonus.

1.7 s vs 3.3 s

It is faster only in batches

Sonnet got 20 replies per call. One reply per call, the way most apps work (a message arrives, the app decides), Jev answered in 1.7 s and Sonnet in 3.3 s. The cost per million replies became $30 for Jev and $1,607 for Sonnet, 53 times more.

91% vs 65%

Jev knows when it is unsure

Jev was sure on 80 of the 100 replies and right on 91% of them. It flagged the other 20, where it was right only 65% of the time. Sonnet gives no such signal: nothing marks the replies where it changes its mind.

Jev on every reply→Sonnet on the 20% flagged

90% right answers for about $93 per million replies, against 93% for $314 with Sonnet alone in batches, or $1,607 one by one. The LLM is kept for the hard cases.

Measured in two races of this demo (100 replies, "What do they think of Episode 1?"): LLMs 20 per call, then one per call. The cascade is computed from the first race's answers, using Sonnet's batch price for the escalated replies.

When to use which

A System One model, when code acts on the answer

  • Classify and route at scale: tickets, emails, comments, documents
  • Smart if-statements: "is this a refund request?" inside normal code
  • Guardrails: screen what goes into and out of an LLM app
  • Score on a rubric: urgency, risk, quality, then branch on the number
  • Pull values out of documents: amounts, dates, names, with their position
  • Turn text into features for a statistical model
  • Real time: a decision in a game loop, a filter on a live chat

An LLM, when a person reads the answer

  • Chat and assistants
  • Write, rewrite, translate, summarize
  • Generate and review code
  • Explain a decision in words
  • Open questions with no list of possible answers
  • Multi-step reasoning and planning, agents that use tools

Quick test: could a smart person answer it in a few seconds by picking from a list? Then it is a System One question.

Better together

In a real product, the two work side by side: the System One model decides fast, the LLM handles what needs words or deep reasoning.

Extract, decide, then write

Clairic: values→Clef: decision→LLM: the reply

Cloudflare's insurance-claim example: Clairic reads the amounts and dates, Clef decides, an LLM writes the letter. 19.3 s instead of 61.7 s and about half the cost of an all-LLM pipeline (Cloudflare's figures).

Routing

decision model→code or LLM or person

Classify each request, then send it to plain code, a specialist LLM, or a human.

Guardrails

check→LLM→check

Screen every message before it reaches the LLM and every reply before it reaches the user.

Cascade

cheap answer→verify→reasoning model

Accept the cheap answer when the check is confident; escalate the rest. Most of the quality, a fraction of the cost.

Filter before the LLM

search→score passages→LLM answers

Score retrieved passages and keep only the relevant ones, so the LLM reads less and invents less.

Triage, then explain

label 1M replies→summarize the top ones

This demo: count opinions on every reply cheaply, then let an LLM write the report for people.

The LLM writes the code

coding agent→program→decision model

A coding agent builds the app; the app calls the decision model at run time. Jev does not replace the agent's LLM.

Limits to keep in mind

  • No text at all: no explanation of an answer, no summary, no chat.
  • You must know the possible answers in advance. An open question needs an LLM.
  • Questions in one request do not see each other: put the context in the state.
  • Wording matters: an option name is all the model sees. Test on real, hard cases.
  • Extraction models read and compute short steps: long calculations and sums over many rows belong in code.
  • Young products: the Decisions API on OpenRouter is in alpha, Clairic is a preview, images and Box are experimental, and the speed and cost figures published by vendors are their own.

If a person reads the output, use an LLM.
If code reads it, ask a System One model.
