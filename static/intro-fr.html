Deux sortes de modèles d'IA, deux sortes de lecteurs

Les LLM écrivent pour des personnes. Les modèles System One, modèles de décision comme Jev et modèles d'extraction comme Clairic, répondent pour du code. Ce que fait chacun, comment il fonctionne, et quand utiliser l'un, l'autre, ou les deux.

☺une personne lit
{ }un programme lit

Les flèches du clavier ou les boutons font passer d'une diapositive à l'autre.

La vraie différence : qui lit la réponse

Les LLM sont faits pour les humains

  • Entraînés à écrire des réponses que les gens préfèrent (RLHF) ou qui passent une vérification, comme un résultat de maths (RLVR)
  • La sortie est du texte : une réponse de chat, un essai, du code, parfois un refus
  • Une personne le lit, le juge et le corrige si besoin

« Voici un résumé des 581 réponses : la plupart des spectateurs ont trouvé l'épisode… »

Les modèles System One sont faits pour le code

  • Entraînés à rendre des décisions avec des probabilités calibrées (RLCD)
  • La sortie est une donnée typée, définie à l'avance : une option, un score, une probabilité
  • Un programme la lit et agit en fonction, sans humain entre les deux
if answer.noul > 0.7:
    route_to_support(ticket)

Le pari de TypeSafe : l'essentiel de l'automatisation par l'IA sera du logiciel qui parle à du logiciel, donc l'interface pour les machines compte plus que l'interface de chat.

D'où vient le nom

Daniel Kahneman, Système 1 / Système 2 : les deux vitesses de la pensée : nous pensons avec deux systèmes.

1

Système 1 : rapide et intuitif

Vous lisez une réponse et vous savez tout de suite qu'elle est en colère. Pas d'étapes, pas de mots dans la tête.

Modèles System One : un jugement rapide, de quelques centaines de millisecondes à une ou deux secondes

2

Système 2 : lent et réfléchi

Vous préparez un voyage ou vérifiez une démonstration étape par étape, en formulant chaque étape.

Les LLM, et encore plus les LLM de raisonnement : ils pensent en écrivant, token après token

Le système 1 est connu pour se tromper. Ces modèles parient qu'un jugement rapide peut devenir fiable s'il est accompagné d'une probabilité honnête.

Même réponse, même question, deux façons de répondre

"The lip sync is off and the voice acting feels flat, but the landscapes in Episode 1 look amazing."
(« Le doublage n'est pas synchro et les voix sont plates, mais les paysages de l'épisode 1 sont superbes. »)

Un LLM écrit la réponse

{"opinion": "mixed"}
  1. Génère un token à la fois, et chacun est facturé
  2. Votre code analyse le texte. Un JSON mal formé, c'est une réponse perdue.
  3. Aucune indication de son degré de certitude

Un modèle de décision note chaque réponse possible

mitigé1,00
négatif0,00
positif0,00
  1. Lit la réponse et les réponses possibles une seule fois
  2. Rend une probabilité pour chaque réponse, toutes en même temps. Il n'écrit rien.
  3. Seule l'entrée est facturée. La réponse est toujours l'une des options.

Sortie réelle de Jev 1.14 sur cette phrase. Le côté LLM est ralenti pour montrer son fonctionnement, il n'est pas chronométré.

Un modèle de décision répond à des questions typées

Vous envoyez un état (le texte ou les données à juger) et quelques questions. Chaque question a un type qui fixe la forme de la réponse.

Noul

Cette affirmation est-elle vraie ?

noul: 0.99

« L'auteur demande à être contacté. » Une probabilité entre 0 et 1.

Choice

Quelle option convient ?

choice: "mixed"

Une option de votre liste, avec une probabilité pour chaque option.

Score

Où sur cette échelle ?

score: 1.36

Des niveaux que vous décrivez (de « aucune critique » à « insultant ») ; le score tombe entre « légère » et « forte ».

Box

Où est-ce dans l'image ?

top, left, bottom, right

Jev, encore expérimental : les bords de l'objet, en fractions de l'image.

Les questions d'une même requête sont traitées en parallèle et ne se voient pas entre elles. Votre code combine les réponses : la logique reste dans le code, là où on peut la tester.

Modèles d'extraction : des valeurs typées tirées d'un texte brut

La deuxième famille de modèles System One, ouverte par Clairic de Cloudflare. Un modèle de décision choisit parmi vos options ; un modèle d'extraction rend des valeurs : un passage du texte, un nombre, une date.

Bonjour, la commande A-88412 est arrivée cassée. J'ai payé 129,90 $ le 2 octobre. Le couvercle est fendu et le carton était trempé.

champ (type)valeurd'après le textep_nullconfiance
order_id (text)"A-88412"caractères 21 à 280,001,00
amount_paid (number, USD)129.90lu0,000,99
paid_on (date)2026-10-02« 2 octobre », résolu0,010,97
damage (text)"Le couvercle est fendu"caractères 82 à 1040,020,93
tracking_number (text)nullabsent du texte1,000,42
  • Les valeurs texte sont des passages avec leur position : on peut les surligner dans la source, et elles ne peuvent pas contenir un chiffre inventé.
  • Un champ absent revient à null avec p_null, au lieu d'une valeur plausible inventée. Le code envoie les valeurs peu sûres à une personne.
  • Tous les champs sont traités en une passe : trente champs coûtent à peu près autant que trois.

Valeurs illustratives, au format de réponse documenté par Cloudflare. Clairic tourne sur Workers AI sous le nom @cf/cloudflare/clairic (preview), 0,10 $ par million de tokens d'entrée, sortie non facturée.

Extraire, calculer, estimer, prévoir

Vous décrivez chaque champ avec un type et une consigne en langage courant. Le type fixe la forme de la réponse.

text

Copier un passage de l'entrée

"A-88412", span [21, 28]

number

Lire ou calculer un nombre

141.59

Prix plus taxe : une ou deux étapes de calcul.

date, time, duration

Une date ou une durée valide

2026-10-02

« jeudi prochain » résolu par rapport à une date de référence.

list

Toutes les valeurs qui correspondent

["A-88412", "A-88415"]

Dans leur ordre d'apparition.

estimate

Une valeur que le texte ne donne pas

médiane 415 000, 80 % : 370 k à 470 k

Le prix d'une maison d'après des ventes comparables, dans des bornes que vous fixez.

forecast

Les prochains points d'une série

un intervalle par point

Des tendances simples, jusqu'à 64 points.

Le conseil de Cloudflare lui-même : laisser Clairic lire les valeurs et le code faire les longs calculs. Les calculs en plusieurs étapes et les sommes sur beaucoup de lignes ne sont pas encore fiables.

Une probabilité sur laquelle on peut agir

Calibré veut dire : parmi toutes les réponses données avec une probabilité de 0,8, environ 80 % sont justes. Le code peut donc fixer une règle dessus.

sous 0,3considéré comme nonaction automatique
de 0,3 à 0,7pas sûrenvoi à une personne ou à un plus gros modèle
au-dessus de 0,7considéré comme ouiaction automatique
  • Les seuils sont à vous, fixés selon le coût de chaque erreur : bloquer un bon message, ou en laisser passer un mauvais.
  • Un LLM peut écrire « j'en suis sûr à 90 % », mais ce chiffre est du texte, pas une probabilité mesurée.
  • La calibration vaut sur un grand nombre de réponses, pas pour chacune. Vérifiez-la sur un échantillon étiqueté avant de lui faire confiance.

  • Les petits modèles de décision égalent ou battent les LLM de même prix en bonnes réponses, et n'en perdent aucune.
  • Sur les 581 réponses, Llama 3.1 8B a cassé le format JSON 441 fois : ces réponses ont été perdues.
  • Les modèles de décision ne sont pas toujours les moins chers : un petit LLM qui traite les réponses par lots peut coûter moins. Ce qu'ils apportent : un appel par élément, aucune analyse de texte, et une probabilité pour chaque réponse.

Ici, Sonnet semble plus rapide et plus juste que Jev. La diapositive suivante explique pourquoi cette lecture est trompeuse.

« Mais Sonnet gagne. Pourquoi prendre Jev ? »

93 %

Sonnet est noté contre lui-même

Le corrigé, ce sont les étiquettes de Sonnet lors d'une exécution précédente : « bonnes réponses » veut donc dire « d'accord avec Sonnet ». Malgré ça, Sonnet change d'avis sur 7 à 9 % des réponses d'une exécution à l'autre. Tout modèle qui juge comme lui est avantagé.

1,7 s contre 3,3 s

Il n'est plus rapide que par lots

Sonnet a reçu 20 réponses par appel. Avec une réponse par appel, comme dans la plupart des applications (un message arrive, l'app décide), Jev a répondu en 1,7 s et Sonnet en 3,3 s. Le coût par million de réponses est devenu 30 $ pour Jev et 1 607 $ pour Sonnet, 53 fois plus.

91 % contre 65 %

Jev sait quand il n'est pas sûr

Jev était sûr sur 80 des 100 réponses et en a eu 91 % de justes. Il a signalé les 20 autres, où il n'avait que 65 % de justes. Sonnet ne donne aucun signal de ce genre : rien ne marque les réponses où il change d'avis.

Jev sur chaque réponse→Sonnet sur les 20 % signalées

90 % de bonnes réponses pour environ 93 $ par million de réponses, contre 93 % pour 314 $ avec Sonnet seul par lots, ou 1 607 $ une par une. Le LLM est gardé pour les cas difficiles.

Mesuré sur deux courses de cette démo (100 réponses, « Que pensent-ils de l'épisode 1 ? ») : LLM à 20 réponses par appel, puis à une par appel. La cascade est calculée à partir des réponses de la première course, au prix par lots de Sonnet pour les réponses transmises.

Quand utiliser lequel

Un modèle System One, quand du code agit sur la réponse

  • Classer et router en masse : tickets, e-mails, commentaires, documents
  • Des « if » intelligents : « est-ce une demande de remboursement ? » dans du code ordinaire
  • Garde-fous : filtrer ce qui entre dans une app LLM et ce qui en sort
  • Noter selon une grille : urgence, risque, qualité, puis décider selon le chiffre
  • Extraire des valeurs de documents : montants, dates, noms, avec leur position
  • Transformer du texte en variables pour un modèle statistique
  • Temps réel : une décision dans une boucle de jeu, un filtre sur un chat en direct

Un LLM, quand une personne lit la réponse

  • Chat et assistants
  • Écrire, réécrire, traduire, résumer
  • Générer et relire du code
  • Expliquer une décision avec des mots
  • Questions ouvertes, sans liste de réponses possibles
  • Raisonnement et planification en plusieurs étapes, agents qui utilisent des outils

Test rapide : une personne compétente pourrait-elle répondre en quelques secondes en choisissant dans une liste ? Alors c'est une question pour un modèle System One.

Plus forts ensemble

Dans un vrai produit, les deux travaillent côte à côte : le modèle System One décide vite, le LLM prend ce qui demande des mots ou un raisonnement poussé.

Extraire, décider, puis écrire

Clairic : valeurs→Clef : décision→LLM : la réponse

L'exemple de sinistre d'assurance de Cloudflare : Clairic lit les montants et les dates, Clef décide, un LLM écrit le courrier. 19,3 s au lieu de 61,7 s et environ deux fois moins cher qu'un pipeline tout LLM (chiffres de Cloudflare).

Routage

modèle de décision→code ou LLM ou personne

Classer chaque demande, puis l'envoyer à du code simple, à un LLM spécialisé ou à un humain.

Garde-fous

contrôle→LLM→contrôle

Filtrer chaque message avant qu'il n'atteigne le LLM, et chaque réponse avant qu'elle n'atteigne l'utilisateur.

Cascade

réponse bon marché→vérification→modèle de raisonnement

Garder la réponse bon marché quand la vérification est sûre, transmettre le reste. L'essentiel de la qualité pour une fraction du coût.

Filtrer avant le LLM

recherche→noter les passages→le LLM répond

Noter les passages retrouvés et ne garder que les pertinents : le LLM lit moins et invente moins.

Trier, puis expliquer

étiqueter 1 M de réponses→résumer les principales

Cette démo : compter les opinions sur chaque réponse à bas coût, puis laisser un LLM écrire le rapport pour les humains.

Le LLM écrit le code

agent de code→programme→modèle de décision

Un agent de code construit l'app ; l'app appelle le modèle de décision à l'exécution. Jev ne remplace pas le LLM de l'agent.

Les limites à garder en tête

  • Aucun texte : pas d'explication d'une réponse, pas de résumé, pas de chat.
  • Il faut connaître les réponses possibles à l'avance. Une question ouverte demande un LLM.
  • Les questions d'une même requête ne se voient pas : mettez le contexte dans l'état.
  • La formulation compte : le nom d'une option est tout ce que le modèle voit. Testez sur des cas réels et difficiles.
  • Les modèles d'extraction lisent et font des calculs courts : les longs calculs et les sommes sur beaucoup de lignes relèvent du code.
  • Des produits jeunes : l'API Decisions d'OpenRouter est en alpha, Clairic est en preview, les images et Box sont expérimentales, et les chiffres de vitesse et de coût publiés par les fournisseurs sont les leurs.

Si une personne lit la sortie, prenez un LLM.
Si du code la lit, demandez à un modèle System One.
